# Staff spreadsheet inventory import

The staff CSV/XLSX path normalizes to `StaffImportRow`, then shares PDF category/location resolution, asset matching, `StaffImportProposal`, review, the import ledger and canonical Apply services. No schema changes are needed.

CSV uses csv-parse for comma, semicolon and tab detection, BOM handling and quoted fields. XLSX reads stored XML values across sheets, including formula caches; formulas are never evaluated. Macros and external workbook links remain rejected.

Header detection examines the first 40 rows for multiple known concepts and nearby data. Clear inventory tables are included automatically; Notes/Instructions sheets are skipped. Staff can specify a sheet and header row under Spreadsheet options before uploading again. Duplicate/ambiguous column layouts and invalid rows remain visible for review. Metadata, blanks, totals, VAT and freight are excluded.

Spreadsheet rows preserve source sheet/row, raw description, manufacturer, supplier SKU, MPN and quantities. Received/shipped quantities take precedence; ordered-only rows cannot become received stock. Negative/fractional quantities require correction. Duplicate SKU/MPN identities remain separate and require review; quantities are not silently combined.

Semantic enrichment uses the existing strict helper contract in sequential batches of 30 concise rows. Exact source references join results back to parsed rows; helper quantities cannot override parsed quantities. Invalid/missing helper results retain deterministic rows with diagnostics. The helper's credential allowlist is unchanged. All writes still require the existing explicit Apply action.

Product metadata enrichment runs inside the same proposal flow. It uses a useful source description first, then a verified concise helper description when product identity is clear; an existing Shelf description remains the default for an existing model. Image discovery runs automatically for every distinct new product identity, with at most six lookups at once. It checks image/product URLs included in the source first, then uses the optional Brave Search web provider to discover product pages from prioritized manufacturer+MPN, manufacturer+model, exact part number, and manufacturer+description queries. Search results are ranked with configured manufacturer domains first, then normalized manufacturer-domain evidence, configured distributors, supplier-domain evidence, and other exact matches. A candidate page must independently confirm the model/manufacturer or exact MPN/SKU before its structured Product image or OpenGraph image can be used. Bounded Openverse results with strict MPN or manufacturer/model metadata matching remain a fallback. Rows with weak matches keep no image suggestion.

Text-only PDF invoice image lookup requires the server-side `BRAVE_SEARCH_API_KEY` environment variable. Brave Search requires an active provider plan and an API key; do not expose this key to the browser or Claude helper. Without it, Shelf can still use source-provided product/image URLs and Openverse matches, but cannot discover official manufacturer product pages from invoice text alone. Manufacturer-domain overrides use the optional `IOIO_PRODUCT_IMAGE_MANUFACTURER_DOMAINS` JSON map; known distributor domains use `IOIO_PRODUCT_IMAGE_TRUSTED_DISTRIBUTOR_DOMAINS` as a comma-separated allowlist. Search results are candidates only: Shelf fetches each result page itself and validates identity before accepting a product image.

External pages are fetched through Shelf's SSRF-safe network helper, with a 2 MB HTML page cap, a 512 KB search-response cap, 8 MB image-download cap, five-second timeout, redirect revalidation, and no credentials forwarded from the search provider to result pages. Only JPEG, PNG, and WebP with matching MIME and file signatures are accepted. Shelf decodes and bounds image dimensions, then resizes/re-encodes to static WebP; proposal images are capped at 128 KB (manual uploads at 64 KB). Automatic previews are persisted in Shelf's organization-owned Image table and referenced by ID in the proposal, rather than embedded as base64 in operation JSON. The canonical upload path additionally checks processed original and thumbnail bytes against a 2 MB cap before storage. Staff can inspect, remove, or replace an image in review. Strongly matched validated images are selected by default; image lookup or processing failure leaves the row importable. Existing model images are preserved and skipped by automatic lookup. Apply uses Shelf's canonical image services, and image data remains proposal/review data until Apply. Individually tracked items store metadata on their AssetModel; quantity-tracked stock pools keep Shelf's model-link rules and store accepted descriptions/images on the stock asset.

Limits remain 5 MB and 1,000 product rows. Source-specific provenance lives in existing review details. Parsing logs counts, selected sheet/header and helper batch status without logging row contents.

Import readiness is calculated by `validateImportRowForApply` from the reviewed product identity, quantity, existing/new choice, tracking, and required category/location IDs. Historical `CONFLICT`/`reviewState` values do not gate Apply. The server validates canonical records again and returns `readyCount`, `blockedCount`, and per-row issue codes/messages before claiming inventory writes. Image and description enrichment never block readiness.

Row Import applies that row immediately through the existing ledger. Import selected validates only the selected rows and blocks the entire selected batch if any need review, listing all blocked products; staff can fix those rows or select just the ready ones. Remaining draft edits and approvals survive partial imports. Imported rows are excluded from later validation and retries return an explicit already-imported issue. The dashboard panel posts to the same `/staff/import` action; the legacy Home handler also returns structured readiness responses.

Real product-image verification, exact configuration, recorded probe results, temporary-preview retention, failure reason codes and the quantity-stock/AssetModel boundary are documented in [ioio-product-image-verification.md](./ioio-product-image-verification.md).
